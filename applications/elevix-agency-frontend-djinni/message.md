## English

Your product is a gambling MVP, and my most recent contract was a live iGaming platform, so the
money rules and access control there are familiar from the inside, not from a distance. I built
per-brand GEO access rules end to end for it (identity, gateway, wallet, bonus, casino,
notification): schema, a shared decision function, gateway counters, threshold alerts, an admin
CRUD and the React admin UI. Alongside that was money-correctness work - idempotent withdrawals,
single-statement bonus expiry with debit, abuse limits on bonus issuance.

Taking a frontend from nothing to production is something I've done solo three times in a row:
Quextro, an ed-tech platform (React 19, TanStack, Bun and Drizzle on the back), used by British
teachers and students; sportmagaz.com.ua, a sports-equipment store on Next.js 14 with its own
admin panel for 2,000+ products; and consolline.com, the site of a logistics company on Astro, 4
languages, WebGL2 animations. On all three I owned the frontend from the first commit to release,
architecture decisions included.

Node.js and Postgres aren't a "plus" for me, they're daily tools - Drizzle ORM every day,
including hand-written schemas and migrations. AI integrations aren't new either - at Quextro I
built the core LLM feature that extracts questions and topics from PDF exam papers.

Honest about the gap: I haven't built Telegram Web Apps or Mini Apps. sportmagaz.com.ua has a
Telegram bot for order alerts, but that's a different surface than a TWA interface. I'd expect to
pick up the Telegram API quickly, but I'd rather say that upfront than after starting.
